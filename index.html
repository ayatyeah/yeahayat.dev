1. Message Queues (MQ)

What is MQ? A Message Queue helps different parts of an app (services) talk to each other. They do not wait for an answer. One service sends a message, and another reads it later. This is called Asynchronous communication.

  • Decoupling: Services do not need to know about each other.
  • Pub/Sub (Publish/Subscribe): One message goes to many listeners (consumers). Example: An order is created. Billing and Email services both read the message.
  • Point-to-Point (P2P): One message goes to only ONE consumer. Good for tasks (like resizing an image).

Tools

  • NATS: Very fast and simple. Uses "Subjects" (like a name for a message channel). JetStream is a part of NATS that saves messages so they are not lost if a server crashes (persistence).
  • RabbitMQ: Uses "Exchanges" to route (direct) messages to "Queues". Very flexible.
  • Kafka: Saves messages in a "log". Great for massive data and analytics.

2. Transactions & ACID

A transaction is a group of database actions. They must all succeed, or all fail together.

  • A - Atomicity: All or nothing. (If step 2 fails, step 1 is canceled).
  • C - Consistency: Data must be valid and follow rules.
  • I - Isolation: Concurrent (same time) transactions do not break each other.
  • D - Durability: If saved, it stays saved even if power goes off.

PostgreSQL: A SQL database. Very strong ACID rules. Uses BEGIN, COMMIT, and ROLLBACK.
MongoDB: A NoSQL database. Added ACID transactions later to support complex workflows across multiple documents.

2PC (Two-Phase Commit): Used when a transaction uses TWO different databases. Phase 1: Ask "Are you ready?". Phase 2: "Commit!". It is hard and slow.

3. Caching Strategies

What is Caching? Saving frequently used data in fast memory (like Redis) so you do not ask the slow database every time.

  • Cache Hit: Data is in the cache. Very fast!
  • Cache Miss: Data is not in the cache. App asks the database, then saves it to cache.
  • TTL (Time To Live): How long data stays in cache before it deletes itself.
  • Write-through: Save to DB and Cache at the exact same time.
  • Write-back: Save to Cache first (fast), save to DB later. Risky if power goes off.
  • Write-around: Save to DB only. Cache gets data only on the next read.

4. External Integrations & Background Jobs

  • Idempotency: A very important concept! It means if you do the same action many times, the result is the same as doing it once. Example: "Set volume to 5" is idempotent. "Increase volume by 1" is NOT. We use Idempotency Keys so we don't charge a credit card twice if network fails!
  • Webhooks: When an external app (like Stripe or GitHub) sends an HTTP POST request to your app to say "Something happened!". You must verify the signature.
  • Retries: If a job fails, try again. Use Exponential Backoff (wait 1s, then 2s, then 4s) so you do not break the server.

5. Observability & Monitoring

How do we know if our app is healthy?

  • Logs: Text messages about what happened (e.g., "User 123 logged in"). Use Structured Logging (JSON) in Go.
  • Metrics: Numbers and stats over time. (e.g., CPU is at 80%, or 50 requests per second). Used for alerts.
  • Traces: Follows ONE request across many microservices. Uses a Trace ID. Helps find which service is slow.

1. Очереди сообщений (Message Queues)

Что это? MQ помогает разным частям приложения (микросервисам) общаться друг с другом. Они не ждут ответа. Один сервис отправляет сообщение, другой читает его позже. Это называется Асинхронным общением.

  • Слабая связность (Decoupling): Сервисам не нужно знать друг о друге.
  • Pub/Sub (Издатель/Подписчик): Одно сообщение получают много слушателей. Пример: заказ создан, сервисы биллинга и email оба читают это сообщение.
  • Point-to-Point (P2P): Одно сообщение идет только ОДНОМУ консьюмеру (обработчику). Отлично подходит для задач (например, изменение размера картинки).

Инструменты

  • NATS: Очень быстрый и простой. Использует "Subjects" (темы сообщений). JetStream — это надстройка над NATS, которая сохраняет сообщения (persistence), чтобы они не потерялись при сбое сервера.
  • RabbitMQ: Использует "Exchanges" (обменники) для маршрутизации сообщений в "Queues" (очереди).
  • Kafka: Сохраняет сообщения в виде "лога" (журнала). Идеально для огромных объемов данных и аналитики.

2. Транзакции и ACID

Транзакция — это группа действий в БД. Они должны либо все выполниться успешно, либо все отмениться.

  • A - Atomicity (Атомарность): Всё или ничего. Если шаг 2 падает, шаг 1 отменяется.
  • C - Consistency (Согласованность): Данные должны быть валидными и не нарушать правила БД.
  • I - Isolation (Изолированность): Параллельные транзакции не мешают друг другу.
  • D - Durability (Надежность): Если данные сохранены (commit), они не пропадут даже при отключении света.

PostgreSQL: SQL база данных. Строгие правила ACID (использует BEGIN, COMMIT, ROLLBACK).
MongoDB: NoSQL база данных. Добавили поддержку ACID транзакций позже для сложных операций над несколькими документами.

2PC (Two-Phase Commit): Используется для распределенных транзакций (в нескольких БД). Фаза 1: "Все готовы?". Фаза 2: "Сохраняем!". Это сложно и медленно.

3. Стратегии кэширования (Caching)

Что это? Сохранение часто используемых данных в быстрой памяти (например, Redis), чтобы не дергать медленную БД каждый раз.

  • Cache Hit: Данные найдены в кэше. Очень быстро!
  • Cache Miss: Данных нет в кэше. Приложение идет в БД, затем сохраняет ответ в кэш.
  • TTL (Time To Live): Время жизни данных в кэше до их автоматического удаления.
  • Write-through: Данные пишутся в БД и кэш одновременно.
  • Write-back: Данные пишутся сначала в кэш (быстро), а потом асинхронно в БД. Риск потери данных при сбое.
  • Write-around: Данные пишутся только в БД. Кэш обновляется только при следующем чтении.

4. Внешние интеграции и Фоновые задачи

  • Идемпотентность (Idempotency): Важнейший концепт! Это значит, что если выполнить действие много раз, результат будет таким же, как если выполнить его один раз. Это нужно, чтобы при сбое сети мы не сняли деньги с карты клиента дважды. Мы используем Idempotency Keys.
  • Webhooks (Вебхуки): Когда внешнее приложение (например, Stripe) отправляет HTTP POST запрос вашему приложению, чтобы сказать "Что-то произошло!". Обязательно нужно проверять цифровую подпись (signature).
  • Ретраи (Retries): Если задача упала, пробуем снова. Используем Exponential Backoff (ждем 1с, потом 2с, потом 4с), чтобы не положить сервер.

5. Наблюдаемость (Observability) и Мониторинг

  • Логи (Logs): Текстовые сообщения о событиях (например, "Пользователь зашел"). В Go лучше использовать структурированные логи (JSON).
  • Метрики (Metrics): Числа и статистика во времени (например, загрузка CPU 80% или 50 запросов в секунду). Нужны для алертов (Grafana/Prometheus).
  • Трейсы (Traces): Отслеживание ОДНОГО запроса через все микросервисы. Используется Trace ID (OpenTelemetry). Помогает найти, какой именно сервис тормозит.
